## Le concept de drift — pourquoi ton modèle "pourrit" avec le temps

### Le problème de base

Quand tu entraînes un modèle de ML, tu fais une hypothèse implicite énorme : **"le monde de demain ressemblera statistiquement au monde d'hier"** (celui de tes données d'entraînement). C'est l'hypothèse i.i.d. (données identiquement et indépendamment distribuées) que tu vois en cours.

Le problème : dans la vraie vie, cette hypothèse est **fausse**, tout le temps. Le monde change. Et quand il change, ton modèle continue à faire des prédictions comme si rien n'avait bougé — silencieusement, sans crasher, sans erreur visible. C'est ça le vrai danger : un modèle qui driftte ne plante pas, il se dégrade en douceur.

### Les deux grands types de drift

**1. Data drift (ou covariate shift)** — la distribution des **features** (X) change, mais la relation X→Y reste la même.

> Exemple fraude : avant, le montant moyen des transactions était de 50€. Après une période d'inflation, il passe à 65€. Le modèle voit des valeurs qu'il n'a jamais vues à cette fréquence → il devient moins fiable, même si "ce qui définit une fraude" n'a pas changé.

**2. Concept drift** — la relation entre X et Y change elle-même. Le pattern que ton modèle a appris n'est plus valide.

> Exemple fraude : avant, les fraudeurs faisaient de gros montants d'un coup. Maintenant ils font plein de petits montants pour ne pas se faire repérer. La définition même de "à quoi ressemble une fraude" a changé → le modèle applique une règle obsolète.

C'est la distinction la plus importante à maîtriser : **data drift** = les inputs changent ; **concept drift** = la règle du jeu change. Le deuxième est plus grave et plus dur à détecter.

### Pourquoi Evidently (l'outil qu'on utilise) se concentre sur le data drift

Détecter le concept drift nécessiterait de connaître les vrais labels en temps réel (est-ce que c'était vraiment une fraude ?) — ce qui prend souvent des semaines/mois à obtenir (enquête, contestation client...).

Le **data drift**, lui, ne nécessite **aucun label** : tu compares juste la distribution statistique de tes features entre deux périodes. C'est pour ça qu'en pratique, la première ligne de défense en production est presque toujours le monitoring de data drift — c'est un **proxy** rapide qui dit "attention, quelque chose a changé dans les données que je reçois, il est probable que mon modèle se trompe plus".

### Comment on mesure ça mathématiquement (l'essentiel)

Pour chaque feature, Evidently compare la distribution de référence vs actuelle avec un test statistique adapté au type de donnée :

- **Variables numériques** (comme `Amount`, `V1`...) → test de Kolmogorov-Smirnov ou distance de Wasserstein : ça mesure "à quel point ces deux distributions sont différentes"
- **Variables catégorielles** → test du Chi², ou PSI (Population Stability Index)

Si le test dit "distributions significativement différentes" pour une feature → cette feature est "driftée". Si le **pourcentage de features driftées** dépasse un seuil (souvent 50% par défaut, configurable) → on déclare "dataset drift" global.

C'est exactement ce que tu vois dans le champ `share_of_drifted_columns` du JSON qu'on génère dans `drift_check.py`.

### Le lien avec DriftGuard

Ton pipeline fait ceci, dans l'ordre logique :

1. Tu gardes une **fenêtre de référence** (ex: les données sur lesquelles le modèle a été entraîné/validé)
2. Tu compares régulièrement les **nouvelles données entrantes** à cette référence
3. Si le drift dépasse un seuil → tu déclenches une alerte, voire un **ré-entraînement automatique** sur des données plus récentes

C'est cette boucle (mesurer → décider → agir) qui est le cœur du "Ops" dans MLOps — sans elle, tu as juste un modèle qu'on a mis en prod un jour et qu'on espère qu'il continue de bien marcher.
